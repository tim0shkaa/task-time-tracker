# В данном файле описаны принимаемые архитектурные (и не только) решения, а также количество затраченных часов на разработку

## Миграции. Liquibase вместо schema.sql

Можно было бы обойтись без liquibase и просто положить `schema.sql` в resources. Spring подхватил бы его автоматически. Но Liquibase даёт версионирование схемы, возможность откатывать изменения и т. п. В реальной разработке это необходимо, поэтому использовал liquebase, хотя для одной миграции можно было обойтись и schema.sql

## База данных. PostgreSQL вместо H2

H2 упрощает запуск. Не нужен Docker. Но PostgreSQL через Docker Compose поднимается одной командой и парой строчек конфигурации. И исходя из того, что в реальных продакшн проектах используется именно постгрес, решил использовать его

## Lombok

Используется для генерации boilerplate кода. `@Data` даёт геттеры, сеттеры, и т п. `@RequiredArgsConstructor` генерирует конструктор для final полей. Без Lombok entity и DTO были бы раздуты в несколько раз при том же функционале. Также в проектах с Hibernate @Data лучше не использовать, так как там есть ленивая загрузка и она может вызывать проблемы с генерацией equals и hashcode. Поскольку в данном проекте myBatis, то @Data корректно использовать.

## XML маппинги

XML маппинги лежат в `resources/mapper/`. Можно было поместить аннотации прямо на методах интерфейса (`@Select`, `@Insert`). Для простых запросов аннотации удобнее, но XML лучше читается для сложных запросов, и это более принятый подход.

## Optional в MyBatis маппере

`findById` возвращает `Optional<Task>` вместо `Task`. MyBatis поддерживает это из коробки. Возврат `null` это неявный контракт который легко упустить, `Optional` явно говорит что результата может не быть и заставляет обработать этот случай. В сервисе это позволяет писать `.orElseThrow()` вместо ручной проверки на null.

## MapStruct вместо ручного маппинга

Можно было писать маппинг руками через сеттеры. MapStruct просто удобнее, а проблем с тем, что какие-то детали реализации скрыты, обычно не возникает, так как он выдает warning еще на этапе компиляции.

## Разделение пакетов mapper/mybatis и mapper/dto

Оба типа мапперов это интерфейсы, и без разделения они лежали бы вперемешку. Разные подпакеты сразу дают понять что `TaskMapper` в `mybatis/` это работа с БД, а `TaskDtoMapper` в `dto/` это преобразование объектов.

## Интерфейсы для сервисов

Можно было писать сразу классы — Spring не требует интерфейсов. Интерфейс явно декларирует контракт слоя, при написании unit-тестов через Mockito мокировать интерфейс чище чем конкретный класс. Плюс это общепринятая практика в Spring-проектах.

## ResponseEntity вместо @ResponseStatus

В контроллерах используется `ResponseEntity` вместо аннотации `@ResponseStatus` на методах. `ResponseEntity` даёт явный и читаемый контроль над HTTP-статусом прямо в теле метода. `@ResponseStatus` менее заметна и при большом количестве методов легче упустить.

## Authentication вместо @AuthenticationPrincipal UserDetails

В `TimeRecordController` для получения текущего пользователя используется `Authentication` из Spring Security вместо `@AuthenticationPrincipal UserDetails`. Оба варианта работают, но `Authentication` — стандартный Spring Security объект, который не требует дополнительных импортов и работает без лишних зависимостей. `@AuthenticationPrincipal` удобен когда нужен полный объект `UserDetails`, в нашем случае нужен только `username` — `authentication.getName()` достаточно.

## UserDetailsService внутри SecurityConfig

Можно было вынести в отдельный класс. Но там всего два захардкоженных пользователя в памяти, выносить которые в отдельный класс избыточно. Если бы пользователи хранились в БД, то выносил бы в отдельный `UserDetailsServiceImpl` со своим маппером и таблицей.

## Сообщения об ошибках в конструкторе исключений

Сообщения на русском языке захардкожены прямо в конструкторах `TaskNotFoundException` и `InvalidTimeRangeException`. Можно было передавать сообщение снаружи при броске исключения. В принципе это гибче и правильнее если могут быть разные сообщения. Но в нашем случае сообщение для каждого исключения всегда одинаковое независимо от контекста, поэтому хранить его в конструкторе логичнее.

## Swagger OpenApiConfig

Swagger работает и без дополнительного конфига, т к `springdoc-openapi` автоматически сканирует контроллеры и генерирует документацию. Но без `OpenApiConfig` в UI нет кнопки Authorize для JWT токена. Конфиг добавляет схему Bearer Authentication. После этого можно вставить токен один раз и все запросы в Swagger UI будут его использовать.

## Централизованная обработка исключений

Все исключения обрабатываются в `GlobalExceptionHandler` через `@RestControllerAdvice`. Альтернатива: `@ExceptionHandler` в каждом контроллере. При добавлении нового контроллера пришлось бы снова дублировать обработчики. А так Формат ответа об ошибке и HTTP-статусы определены в одном месте и любое изменение затрагивает весь проект сразу.

## Подсчёт времени за период

Учитываются записи частично пересекающиеся с периодом, а не только полностью входящие. Для каждой записи берётся пересекающаяся часть: `min(endTime, to) - max(startTime, from)`. Логика вынесена в Java а не в SQL — читабельнее и проще покрыть тестами.

## @BeforeEach для инициализации тестовых объектов

Тестовые объекты (task, createRequest, timeRecordResponse и т.д.) создаются в методе с @BeforeEach а не внутри каждого теста. Можно было инициализировать их прямо в полях класса, но @BeforeEach гарантирует что перед каждым тестом создаются свежие объекты

## Интеграционные тесты — @Disabled

Интеграционные тесты на DAO-слой написаны через TestContainers, но помечены `@Disabled`. Причина: несовместимость версии Docker API на моём ноутбуке с внутренней библиотекой `docker-java` которую использует TestContainers. Пытался пофиксить часа 2-3, но откуда из глубины системы тянется версия 1.32 при минимальной требуемой 1.40. По итогу пофиксить не получилось ни у меня, ни у claude sonnet 4.6, ни у claude opus 4.7 в extended моде. Сами по себе тесты написаны корректно и должны работать в стандартном окружении, проблема исключительно в локальной конфигурации.
